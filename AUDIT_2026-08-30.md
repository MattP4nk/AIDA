# AIDA — Full Project Audit (2026-08-30)

Independent audit across seven dimensions: security, data layer, game logic, architecture,
client, AI integration, and operations. Every finding below was read in source. Claims that
did not survive verification were dropped or downgraded, and are listed in
[Corrections](#corrections-claims-that-did-not-survive-verification).

**Baseline:** `tsc --noEmit` passes clean on the server (genuinely strict config:
`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`). Client builds (232 kB / 73 kB gz).
`svelte-check` reports 4 errors. `eslint` reports 10 errors. `npm test` cannot start.
Zero test files exist.

---

## The headline

The codebase is well-engineered at the infrastructure layer and broken at the gameplay layer.

Error handling, graceful shutdown, CSRF, login lockout, path sanitization, transaction usage,
and logging discipline are all better than typical for a project this size — and the previous
audit rounds tracked in `PR_REVIEW_FIXES.md` were genuinely completed, not checkbox theater
(spot-checked M19 and L16; both real).

But **the core game loop does not work**. Missions cannot be accepted; when they can be, they
complete on the first event regardless of target; server encryption has no effect; and every
shop purchase fails on a foreign-key violation. These are not edge cases — they are the
primary verbs of the game, and they fail deterministically for every player.

Priority is therefore inverted from what you would expect: fix gameplay correctness first,
security second (the two live security holes are real but narrow), and architecture third.

## P0 — Game is non-functional

### G1. Every mission objective completes on its first event
`server/src/services/missionService.ts:703-715`

`updateObjective` branches on `objective.type === "count"` and `"boolean"`; anything else falls
to an `else` that sets `objective.completed = true` unconditionally. Verified:
`grep -c 'type: "count"\|type: "boolean"' missionTemplatePool.ts` → **0**. All 200+ objectives
use semantic types (`hack`, `steal_count`, `explore`, `earn_credits`), so **every** objective
takes the else branch. `objective.target` is never compared.

Accept "Earn 5,000 credits" → earn 1 credit → objective complete → `allCompleted` at :736 →
full XP/credits/reputation paid.

**Fix:** compare against `target` in the else branch. One conditional restores all mission gating.

### G2. No non-tutorial mission can be accepted
`server/src/services/missionGenerator.ts:181` vs `server/src/services/missionService.ts:528`

Generated missions are written with `status: "available"`. `acceptMission` requires `"assigned"`.
`assignMission` has zero callers. Player runs `missions` → sees 5 → `accept 1` →
*"Mission cannot be accepted in current state"*.

### G3. Every shop purchase fails; granted items are invisible
`server/src/services/shopService.ts:718`, `server/prisma/seed.ts:2963`, `schema.prisma:1213`

`SHOP_CATALOG` ids are bare literals (`"basic_scanner"`). The only `ShopItem` rows are seeded as
`` `seed_${name}` ``. `InventoryItem.shopItem` is a **required** FK. So `buy basic_scanner`
passes every guard, decrements credits, then `tx.inventoryItem.create({shopItemId:"basic_scanner"})`
raises P2003 and the transaction rolls back — surfacing as a generic
*"Purchase failed due to server error"*.

Converse direction: `getPlayerInventory:488` resolves rows through `this.catalog.get(row.shopItemId)`
and filters nulls, so mission- and dungeon-granted `seed_*` items are **silently invisible** in
`scripts` and can never be sold or used.

### G4. Server encryption has no effect anywhere; every player gets root on connect
`server/src/services/serverService.ts:950, 966`

`encryptionLevel` is a small int (`schema.prisma:182`, default 0; content uses 0–10).

- `requiredLevel = Math.max(1, Math.floor(encryptionLevel / 20))` ≡ **1** for any value ≤ 19.
- `baseAccess = Math.max(1, Math.floor((hacking / Math.max(1, encryptionLevel / 10)) * 5))` —
  the divisor is `max(1, ≤1)` ≡ **1**, so a starting player (`hacking: 10`) gets
  `floor(50)` → `accessLevel = min(10, 50) = 10`.

`connectToServer:666` then persists `ServerConnection.accessLevel = 10`, which is exactly what
`checkServerAccess`'s `"hackable"` branch (:725) and `canTraverse`'s `link.requiredAccess`
check (:223) consult. One connect unlocks unrestricted topology traversal.

### G5. Anyone can access any player's home server without hacking
`server/src/services/networkTopologyService.ts:714`

```ts
if (server.isPlayerHome || server.ownerId === userId) {
  return { allowed: true, reason: "Owner access.", ... };
}
```

`isPlayerHome` alone matches **any** home server, not the caller's. This is the only access gate
in the `connect` path (`networkCommands.ts:706`). Bypasses the entire home-defense feature set
(`homeFirewall`/`homeVault`/`homeIds`, `hackService.ts:521-566`) and the honeypot logic at
`fileService.ts:364`, which assumes attackers had to break in.

**Fix:** `server.ownerId === userId` alone.

### G6. Seven objective types compare a boolean to an entity ID
`server/src/services/missionIntegration.ts:173, 200, 249, 267, 333, 384, 460`

Templates set `target: true` (`missionTemplatePool.ts:680,685,690,728,822,878`) while the real
IDs go to `obj.metadata.serverId`/`.fileId` (`serverContentService.ts:2015-2040`). So
`objective.target === targetId` is `true === "cmx…"` — always false. Chained missions
(`connect_server` + `hack_target` + `steal`) record zero progress and are unwinnable.

### G7. Story-arc feature is entirely dead
`server/src/services/storyMissionService.ts:424-442, 486`; `server/src/utils/aiOutputValidator.ts:341`

Two independent blockers:
1. `validateStoryArcPlan` filters steps on `isNonEmptyString(s.description, 10)`, but the prompt
   asks for `narrativeBrief` — `description` is never present, so every step is dropped,
   `steps.length < 2`, and arc creation returns `null` regardless of AI quality.
2. Story missions are never written into `playerProgress.missionProgress`, which is the only
   source `getPlayerMissions` (`missionService.ts:436`) reads. Tutorial and generator both write
   it; story is the outlier.

### G8. `ls -l`, `rm -r`, `cp -r` are all broken
`server/src/services/commandModules/systemCommands.ts:187, 578, 616, 654`

Flags are detected via `args.includes(...)` but the path is taken positionally as `args[0]`.
`ls -l` → path `/-l` → *"Directory not found: /-l"*. These are the documented examples in
`getCommandInfo()`.

## P1 — Security

### S1. `server:connect` bypasses every connection authorization gate
`server/src/sockets/handlers.ts:319-330` → `server/src/services/gameStateManager.ts:501-620`

`connectPlayerToServer` verifies only that the `GameServer` row exists — no ownership,
discovery, reachability, or access check. The legitimate `connect` command enforces
`checkServerAccess()` plus a handshake challenge (`networkCommands.ts:705-826`); the socket
event calls neither. `helpers.ts:51` then resolves `ls`/`cat` against exactly the
`session.currentServerId` the event just set.

An authenticated socket emits `{"serverId": "<any cuid>"}` and reads any server in the game.

**Fix:** move the authorization check into `connectPlayerToServer` so both paths inherit it.
(Your uncommitted removal of `id`/`ownerId` from scan output narrows ID discovery, but that is
defense-in-depth, not the fix.)

### S2. Negative / NaN quantity mints credits — currently masked, armed by any shop fix
`server/src/services/commandModules/shopCommands.ts:320, 347` → `server/src/services/shopService.ts:671-705`

`parseInt(args[1] || "1")` is never range-checked, and no layer below rejects it:
the tokenizer is a naive `split(/\s+/)` (`commandProcessor.ts:311`), and `validateCommand`
(`validators.ts:244`) only blocks `rm`-chaining and backticks. With `quantity < 0`, `totalCost`
is negative, so `credits < totalCost`, the stack check, and the in-transaction re-check are all
false, and `{ credits: { decrement: totalCost } }` **increments**. `NaN` (via `buy x abc`)
defeats every `<` comparison identically.

**This is not currently exploitable** — G3's FK violation rolls back the whole transaction,
including the credit increment. It becomes live the moment the shop IDs are reconciled.
Fix both in the same change.

### S3. Bans do not disconnect, and broadcast the reason to everyone
`server/src/services/commandModules/adminCommands.ts:388, 507`

Both emit `force:disconnect` and rely on the client to hang up. Grep across `client/src`:
**zero listeners**. Combined with the socket auth cache short-circuit at `handlers.ts:206-210`
(token verified once at first packet, never re-checked), a banned user's open socket keeps
serving `command:execute` indefinitely. It is also `io.emit` (global) rather than
`io.to(user:<id>)`, so every online player receives the banned user's ID and the moderator's text.

### S4. Free undetected root via unvalidated `--tools`
`server/src/services/commandModules/hackCommands.ts:786` → `server/src/services/hackService.ts:1626`

`parseTools` returns raw strings with no de-dup and no inventory check; `calculateToolBonus`
adds `effectiveness * 0.5` per entry. Repeating one tool name five times pins `successRate` to
its 0.95 ceiling and `detectionRate` to its 0.05 floor, owning no tools.

### S5. Prompt injection reaching item/credit minting (probabilistic)
`server/src/services/aiAgentTools.ts:194-207` → `server/src/utils/aiOutputValidator.ts:283-290`
→ `server/src/services/architectInterventionExecutor.ts:607-610` → `server/src/index.ts:410-436`

`upload` writes arbitrary player content (`fileCommands.ts:152`). The `search_files` agent tool
queries `fileSystemNode` across **all servers** with no ownership filter and splices content into
the Architect's conversation history. `validateArchitectEvaluation` passes `data: i.data` through
verbatim; `handleCreateMission` casts `reward as any` with no bounds; `grant_token` creates an
`inventoryItem` for an arbitrary `targetId`. The 2-hourly `executeBatch` runs unreviewed.

**Calibration:** `contentPreview` truncates to 200 chars and the Architect chooses its own search
query, so this is a probabilistic channel, not a deterministic exploit — HIGH, not CRITICAL.
The `create_server`/`create_file` tools are correctly gated behind `contentDraft` approval;
the Architect interventions are the gap.

**Also reachable via the same loop:** `get_server_access_keys` returns raw key values and
`get_ai_personas` returns every persona `systemPrompt`, with no allow-list separating lookup
tools from what may appear in generated file content.

### S6. `sanitizeForPrompt` is bypassed by sending two messages
`server/src/services/messageService.ts:1374-1379` vs `:1390-1391`

Turn N's message is wrapped. On turn N+1 the same text is re-read from `personaMessage` and
interpolated **raw** into `conversationLines`. Message 1 = payload, message 2 = "continue".

More broadly the sanitizer is applied at 4 of ~25 prompt-construction sites, and it only strips
tags — it does not defend against plain-language instruction injection inside them.

### S7. AI moderation is fed raw user content and fails open on every axis
`server/src/services/aiService.ts:429-459`; callers `forumService.ts:672, 2004`, `messageService.ts:335`

The player's post is passed verbatim as the user turn with no sanitization. `parsed.safe as boolean`
is an unchecked cast (`"safe": "no"` is truthy → passes), failure returns `{safe:true}`, and in
`createReply` moderation runs fire-and-forget *after* the reply is created and broadcast.

### S8. `NODE_ENV` defaults to `development`
`server/src/config/environment.ts:65`

Un-gates the `/admin` static panel (`middleware/setup.ts:137-141`) and sets `sameSite: "none"`
on the auth cookie (`middleware/auth.ts:23`). A plain `node dist/...` deploy gets both. The admin
*API* is properly `requireRole("admin")`-gated, so this is surface exposure plus cookie weakening.

### S9. Socket rate limiting is per-socket, not per-user
`server/src/sockets/handlers.ts:99-103`

20 commands / 10 s = 120/min, vs `userRateLimit(30)` on the REST path. The limiter closure is
created inside `io.on("connection")`, so N sockets on one JWT give N × 120/min. There is also no
`io.use()` connection-level auth and no per-IP socket cap — `/socket.io/` is not covered by the
`/api` rate limiter.

### S10. Lower-severity, verified
- **`story <arcId>` IDOR** — `storyMissionService.ts:720` is a bare `findUnique` with no ownership
  filter (the abandon path checks correctly).
- **`report file` reads Prisma-direct with no permission check** —
  `playerInfoCommands.ts:1461-1486` publishes 100 chars of an uncattable file to the whole faction.
- **Auth cache precedes verification** — `middleware/auth.ts:112-117` returns on cache hit before
  `jwt.verify`, so a token expiring mid-window stays valid up to 60 s. Not poisonable.
- **`jwt.verify` omits `algorithms`** — `auth.ts:120, 218, 268`, `routes/auth.ts:482`. jsonwebtoken 9
  pins HS\* for string secrets so the confusion path is blocked; pin `["HS256"]` explicitly anyway.
- **Dead `hashPassword` hardcodes 10 rounds** — `utils/auth.ts:8-11`, ignoring `BCRYPT_ROUNDS`.
  Unused today, a trap for the next caller. Same inconsistency at `adminCommands.ts:719`.

### Verified sound (no action)
Prisma has exactly one raw query and it is a constant — no `$queryRawUnsafe` anywhere.
Virtual-FS traversal is properly clamped (`pathSanitizer.ts:31-51` + `serverId`-scoped tree walk).
The admin API gate is real. Login has per-IP + per-IP-username lockout with constant error text
(no enumeration). CSRF is JWT-bound with `timingSafeEqual`. CORS rejects wildcards.
**Client XSS: clean** — exactly one `{@html}` (`Terminal.svelte:1689`), escaping applied before
interpolation, and the regex is not ReDoS-prone.

## P1 — Data layer

### D1. Migrations are not in the repository at all
`.gitignore:41` (`*.sql`)

```
$ git check-ignore -v server/prisma/migrations/0001_baseline/migration.sql
```

provision a database. There is also no `migration_lock.toml`, and `package.json` defines only
`db:migrate` (`migrate dev`) — no deploy-safe script.

**Fix:** `!server/prisma/migrations/**/*.sql`.

### D2. The local migration has drifted from the schema
`server/prisma/migrations/0001_baseline/migration.sql`

Verified absent from the migration but present in `schema.prisma` and required by live code:

| Missing | Used at |
|---|---|
| table `message_reports` | `messageService.ts:1487-1534` |
| `messages.is_hidden` | `messageService.ts:534, 573, 607` — every inbox query |
| `key_fragments.status` | fragment brick logic |
| `player_progress.commands_executed`, `successful_hacks`, and 5 siblings | `commandProcessor.ts:602`, `hackService.ts:2247`, `missionService.ts:879` |

(`is_hidden` exists on six *other* tables — not `messages`.) The project has been running on

### D3. `missionProgress` JSON blob has four uncoordinated writers
`missionService.ts:804-893, 1389-1443`; `missionGenerator.ts:172-203`; `tutorialService.ts:954-981`

Whole-blob read-modify-write with no transaction and no optimistic concurrency, two of them on
background timers. The 15-minute expiry sweep reads at T0; a player completes a mission at T0+50ms;
the sweep writes its stale copy at T0+200ms, reverting `status` to `"active"`. The
`"already completed"` guard at :819 then passes again → **rewards granted repeatedly**.

`missionGenerator.ts:95→200` is the worst case: it reuses a snapshot taken *before* minutes of
AI-backed provisioning.

### D4. Credit double-spend: the in-transaction guard takes no lock
`server/src/services/shopService.ts:695-706`

`findUnique` inside a `READ COMMITTED` transaction takes no row lock. Two concurrent buys at
1000 credits for a 600-credit item: both SELECT 1000, both pass, first commits at 400, second
re-reads 400 and decrements to **−200** — both items granted. No `CHECK (credits >= 0)` exists.

**Fix:** conditional `updateMany({ where: { userId, credits: { gte: totalCost } } })` + rowcount
check, or `isolationLevel: Serializable`.

Same pattern, no transaction at all: `aliasService.ts:48→63`.

### D5. Mission rewards overwrite concurrent writes
`server/src/services/missionService.ts:1060, 1087, 1092`

`updateData.credits = progress.credits + rewards.credits` — an absolute write from a stale read,
outside any transaction, while `hackService.ts:2298` concurrently issues `{ increment }`. The
mission write silently erases the hack's award. `shopService.ts:705` does this correctly.

Also: `completeMission` writes mission status (:875, :884) and calls `grantRewards` (:893) as three
uncoordinated statements — a crash between them marks the mission complete with zero rewards paid.

### D6. Duplicate fragment claims
`server/src/services/keyFragmentService.ts:1009-1029`

The comment at :1010 claims *"findUnique inside a transaction provides serializable reads"* — it
does not. Two players cracking the same fragment both read `heldByUserId = null`, both pass
validation, both update. One wins the row, but **both** receive `{claimed: true}`, both get a
discovery row, and both run `updatePlayerCounters` — permanently inflating the loser's
`StoryProgress.swordFragments` and potentially unlocking the endgame early.

### D7. Missing unique constraints the code assumes
- `InventoryItem` (`schema.prisma:1192`) — no `@@unique([userId, shopItemId])`, but every path
  assumes one row per pair. Concurrent shop + mission grant → two rows → `getItemQuantity` reads
  only the first → **`maxStack` permanently bypassable**, and `sellItem` drains only one row.
- `FileSystemNode` (`schema.prisma:246`) — no `@@unique([serverId, parentId, name])` while
  `resolvePath` walks with `findFirst` per segment. Content provisioning racing a player `touch`
  produces two same-named nodes; `cat` and `rm` can hit different rows.

### D8. Skill caps are breakable
`server/src/services/hackService.ts:2298-2307`

`increment: Math.min(gain, 100 - progress.hacking)` computed from a read outside any transaction.
Two concurrent completions at 99 both compute `min(gain, 1)` → **101**.

Worse, `fragmentCommands.ts:681` increments `hacking` by 20 with **no cap at all**, and
`successChance = 0.4 + (hacking/100)*0.3` (:667) is unclamped — an unbounded skill-farming loop.

### D9. Missing indexes on hot paths
`schema.prisma:675` (`Mission`) has only `@@index([storyArcId])`, while:
- `missionService.ts:1364` — `findMany({ where: { status, difficulty: {gte,lte} }, orderBy })`,
  **no `take`**, full seq scan + sort over a continuously-growing table
- `tutorialService.ts:565` — `findFirst({ where: { assignedTo, ... } })`, no index on `assigned_to`,
  on every persona message

`missionService.ts:1390` — `playerProgress.findMany()` with no `where`, `select`, or `take` on a
15-minute timer, pulling four JSON blobs per row for every player.

### D10. Lower-severity, verified
- **`ipService.ts:152-197`** — `generatePlayerHomeIP` picks an octet with no reservation, outside
  the registration transaction; collision → unique violation → 500 with no retry. Hard ceiling of
  254 player subnets.
- **`serverService.ts:642-680`** — `currentConnections` incremented even when reusing an existing
  connection (the existing-branch `update` is entirely commented out); decremented once. Racing
  connects also leave a dangling `is_active` row that three call sites treat as **live access to a
  server the player already left**.
- **`serverContentService.ts:1731-1743, 1892`** — N+1 `count()` per server on the boot path.
- **Missing FKs** — `ServerAccessKey`, `ServerConnection`, `DiscoveredLink`, and all of `Bounty`
  have `user_id` columns with no constraint. No code deletes a `User` today, so this only bites
  on manual/admin deletion.
- **`forumService.ts:2210-2280`** — vote row, denormalized `post.votes`, and author reputation are
  three separate statements; a crash between them leaves permanent drift with no reconciliation.
- **`contentQueueService.ts:334-350`** — job claiming is in-memory with no `where: {status:"pending"}`
  guard on the update; a second instance or restart-requeue double-provisions.

### Verified sound
PrismaClient is a proper singleton with pool params and `$disconnect` on shutdown.
Registration (`routes/auth.ts:65-192`) is fully transactional. `sellItem` and `equipItem` correctly
mutate inside their transactions. Message inbox/sent queries are bounded.

## P2 — Reliability and correctness

### R1. Crash path exits 0 — supervisors will not restart
`server/src/lifecycle.ts:137-145` → `:121`

`uncaughtException` and `unhandledRejection` both route into `gracefulShutdown`, which ends at
`process.exit(0)`. systemd `Restart=on-failure`, Docker `--restart on-failure`, and Kubernetes all
read that as success. **Silent permanent outage after any uncaught error.**

Compounding: any unhandled rejection anywhere tears down the whole multiplayer server.
The code is unusually disciplined about this, but `handlers.ts:117-124` floats
`handleServerConnect(...)` with no `.catch` and the callee has no try/catch — one refactor away
from a remote shutdown primitive.

### R2. `NaN` defeats every config range check
`server/src/config/environment.ts:56-62`

`getEnvNumber` returns `parseInt` with no `isNaN` guard; `validateConfig` range-checks with `<`/`>`,
and all NaN comparisons are false. Concretely: `MAX_FILE_SIZE_MB` feeds `middleware/setup.ts:87,94`
→ `limit: "NaNmb"` → `bytes()` returns `null` → **body size enforcement silently disabled**
(GHSA-v422-hmwv-36x6). Also `PORT=<typo>` → `listen(NaN)` → random port.

### R3. Client never learns its own user ID; hack alerts are dead code
`client/src/App.svelte:55-58, 80`

`socketService.reconnect()` calls `disconnect()`, which sets `this.socket = null` **synchronously**,
then schedules `connect()` 100 ms later. The next line's `getSocket()` therefore always returns
`null`, so the `if (socket)` block never runs — and `App.svelte:80` is the **only** `setUserId`
call site. `getCurrentUserId()` is permanently `null`, so the "your system has been compromised"
alerts at `socket.ts:311, 326` never fire for anyone.

### R4. Trace completion is unreachable
`server/src/services/traceService.ts:166-196`

`newProgress >= 100` requires `elapsed >= totalDuration`, which the expiry branch at :153 already
consumed via `continue`. Progress climbs to 99 then flips to `"expired"`. `trace:completed` never
fires and `trace.evade` is pointless — waiting always wins.

### R5. Two service calls with wrong arity, both silently swallowed
- `hackService.ts:1883` — `initiateTrace(attackerId, serverId, evidenceLevel)` against a 4-parameter
  signature (`traceService.ts:58`). `initiatedBy` receives a serverId, `serverId` receives a number,
  `evidenceLevel` is `undefined`. Prisma throws; caught at :1890. **No `ActiveTrace` row is ever
  created** from the countermeasures path. The correct 4-arg call is at :1239.
- `hackService.ts:1976` — `onFactionServerHacked` called with an object literal against a positional
  4-arg signature (`personaService.ts:775`). Throws, swallowed at debug level. Faction AI is never
  notified of detected intrusions.

Both compile only because `getService<any>` (`hackService.ts:1882`) erases the contract. This is
the concrete cost of the 45 `getService<any>` sites.

### R6. Session destroyed by userId kills live sessions
`server/src/sockets/handlers.ts:591`

Disconnect calls `handleDisconnect(socketId)` → destroys by `userId`. The socket-aware variant
(`gameStateManager.ts:1193`) has **no callers**. Compounded by `handlers.ts:260-267`, which reuses
an existing session on re-auth without rebinding `session.socketId`. After a reconnect blip, the
old socket's delayed disconnect kills the new session, and the new socket never joins
`server:<id>` — so server-room events silently vanish.

### R7. `timeLimit` unit mismatch: nothing expires, everything gets max bonus
`server/src/services/missionGenerator.ts:331-335, 552`

Templates define seconds; the generator multiplies by 1000; consumers multiply again
(`missionService.ts:357, 999`). A "1–2 hour" mission expires in **~41 days**, and
`calculateRewards:997`'s `timeElapsed < timeLimit*1000` is always true with `timeRatio ≈ 0`, so
**every** completion receives the max +50% speed bonus.

Related: every other "performance" multiplier is also constant —
`bonusObjectivesCompleted = max(0, completed - total)` ≡ 0 (:855), `stealthScore` reads
`metadata` that nothing ever writes ≡ 100 (:836), `efficiencyScore` ≡ 100 on the completion path
(:845). Every mission pays `floor(base * 1.85)`.

### R8. Rewards granted to a nonexistent column
`server/src/services/darknetDungeonService.ts:1136`, `server/src/services/missionService.ts:1043-1096`

`skillPoints` is not a column on `PlayerProgress` (verified: no match in `schema.prisma`). The
dungeon reward table hardcodes `{xp: 5000, skillPoints: 2}`, so the update always throws and
`safeExecute` swallows it with no rethrow. A player conquers a 7-day dungeon, is promised
"5,000 XP + 2 Skill Points", and receives **nothing — not even the XP**. `conquerVault` still
returns `{conquered: true}` and schedules regeneration. Same silent drop at `tutorialService.ts:212`.

### R9. Encryption is a data-loss trap
- `hackCommands.ts:982` — a successful `crack.dict/mask/pattern` clears `isEncrypted` and
  `encryptionKey` while leaving **ciphertext in `content`**. `readFile` only decrypts when
  `isEncrypted` is true, so the file is permanently unreadable and the key is gone.
- `fileCommands.ts:471-494` — `encrypt` with no password generates a random key and never surfaces
  it. `decrypt` then refuses forever. The only escape is `crack`, which triggers the above.
- `fileCommands.ts:469-488` — the original is deleted and the temp backup unconditionally deleted
  **before** `finalResult.success` is checked; a failure loses both copies.
- `hackCommands.ts:810` — the crack branch keys on `error === "ENCRYPTED"`, but provisioned
  encrypted files fail with `"DECRYPTION_FAILED"` (`serverContentService.ts:2443` sets
  `isEncrypted: true` with **no key** and plaintext content). The minigame is unreachable for all
  generated content.

### R10. `scryptSync` blocks the event loop on every encrypted read
`server/src/services/fileService.ts:1387, 1417`; `server/src/services/messageEncryptionService.ts:44, 150`

Default scrypt parameters cost ~50–100 ms of non-yielding CPU. Every `cat` of an encrypted file
